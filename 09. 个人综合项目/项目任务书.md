# 个人综合项目任务书

课程：《云计算与大数据处理》。形式：个人完成。本项目综合运用前八个实验的方法，要求同学们完成可运行、可解释、可复建的个人成果。

## 本章身份、截图与提交验收

本章使用实验/项目号 **09**。先登记本人学号，再按 [学号与提交验收](../docs/学号与提交验收.md) 保存运行 JSON/HTML、原始结果和截图。课程 CLI 的 `lab01`—`lab08` 保留各自固定章号；`identity --lab 09` 不会改变这些命令的输出编号。综合项目用 `capture --lab 09 --stage <阶段名> -- <实际子命令>` 包装课程命令、独立脚本或预期故障的实际运行，才生成项目 09 的结果视图，保存为 `outputs/lab09/evidence/<run_id>-<stage>.json` 和同名 HTML；内层课程产物仍保留原章号。项目 HTTP 服务另在新启动终端设置 `$env:BDP_EXPERIMENT_ID='09'` 后再启动，响应与存档显示 09；常驻服务不使用 capture 包装。

所有用于评分的结果及失败/恢复截图必须原生显示**学号、实验/项目号 09、run_id，与真实结果同屏**。在 Chrome 打开生成的 HTML 或服务证据页截图；仅文件名、报告首页、另贴学号图、后期叠字均不合格。提交 `evidence/` 与报告后，按公共说明运行 `submission-manifest`，填写本章编号、提交目录和报告路径后生成清单。机器核对 JSON 身份，授课老师逐张复核截图；无学号、`UNREGISTERED`、身份或原始结果不一致、缺少人工复核，均不能通过验收，退回补证。每张评分截图必须为本章 09；前章 JSON 可按原编号引用，但不能拿前章截图替代。跨章结果用 `capture --lab 09` 重新生成本章原生视图。HTML 与同名运行 JSON 成对提交，`*.identity.json` 随原始文件一并提交。哈希仅作文件一致性核对。此规则是验收前提，评分总分仍为 100 分，基础路径与模型路径同分。

## 1. 项目目标与最小范围

把前八次实验的组件组织成一个有明确用户、数据、计算、规则查询与服务接口的数据产品。交付必须包括：**整体方案、可重建数据、可运行 MVP、独立实现、验收数据、实际结果和失败恢复证据**。

MVP 指能从输入走到用户结果的最小可用版本。例如“使用者提交问题，服务返回模拟服务的使用量统计和题设规则证据，并说明数据版本”。请同学们在本人笔记本上实现完整的数据处理和 HTTP 查询路径，并用下文的验收项验证。

继续使用前八次实验的 Windows/Python 环境并复用课程组件。项目的独立价值必须体现在至少两个关联改动中：

1. 一项数据处理或可靠性改动，例如新的数据质量规则、分组指标、增量状态逻辑、删除传播或分区策略。
2. 一项下游消费改动，例如新的受控统计查询、检索规则、证据输出、缓存失效或服务验收逻辑。

两项改动应围绕同一个用户问题，具有前后因果关系。更换标题、修改配色、替换几条文案、直接重跑八个脚本，均不足以形成个人项目。可以复用已有源代码，但需指出复用与本人修改的范围。

## 2. 可选方向

选一个方向即可。自拟题目须具有相同交付和工作量，不因题目更大而得到更高分。

| 方向 | 具体用户问题 | 建议独立改动 | 项目范围 |
|---|---|---|---|
| A 模拟服务用量与成本解释 | 使用者想知道哪个模拟服务用量异常，以及题设规则提供什么处置依据 | 增加按服务/模型统计的模拟成本或失败率；增加受控统计接口与规则引用 | 固定模拟费率、固定服务与阈值；不对接支付、不自动关闭服务 |
| B 可信规则更新服务 | 查询者与维护者按可见范围读取不同版本的规则，撤回材料不能继续被引用 | 增加版本/撤回一致性规则；实现索引或缓存更新与旧版本拒绝 | 约 20—40 篇虚构短规则；不做复杂 PDF/OCR 和完整账号系统 |
| C 数据管线运行诊断 | 使用者想解释模拟服务记录中的延迟、重复事件或处理失败 | 增加可复算诊断指标；用固定工具提供统计和相关说明文档 | 1—2 类异常、1—2 个诊断查询；不构建任意代码执行 Agent |

“模拟服务使用分析与规则查询平台”是本项目的统一练习场景。同学们在本人笔记本上使用合成服务记录和虚构规则，完成数据分析与规则查询。调整字段时须重新验证数据契约和完整处理链路。

## 3. 必须保留的数据与系统能力

### 3.1 数据层

保留原始层、合法/去重层、分析或服务层，记录输入与产物的散列、版本和生成参数。结构化数据至少含稳定记录 ID、时间和能够聚合的数值；知识数据至少含文档 ID、版本、可见范围和来源说明。写出重复、非法、晚到、撤回与不相关数据的处理规则。

默认可继续使用课程 20,102 行原始事件作为集成数据；另外建立本人可手算的 8—20 条边界事件。不能仅靠数据行数证明“大数据能力”；要提交至少一次列式/分区/并行选择的正确性与代价比较。

### 3.2 计算与恢复层

至少一个批处理结果有独立参照算法或手算验证；至少一个增量路径完成“首次处理—重复输入—受控中断—恢复”。必须指出事务作用范围，不能把输出前后相等但数据根本没被处理当作幂等成功。

可以复用 Dask 多进程和 SQLite 微批；报告说明本机实验的局限。分布式 workers 比串行更慢是可接受结果，但需要解释数据规模、启动、调度与传输开销。

### 3.3 规则检索与证据应用层

提供可追溯检索与证据回答，或将统计数据作为受控工具结果供给查询。至少支持一个不可回答情形和一个权限不满足情形。同学们可以选择词法检索 + 确定式摘录基础路径，也可以选择实验 5/6 的 BGE + 本地 Qwen 模型路径；两者分值相同，都须完成同一组版本、权限、引用和 dev/test 验收。提交时准确标明实际选择的检索器和生成器。

新建不少于 12 个本人核对的问答验收项，至少 6 个可回答项、2 个无答案项、2 个权限项、2 个更新/撤回项。类别可在问题内容上交叉，但验收项应分别指明用户角色、文档状态、预期证据和规则。开发用题与最终验收用题分离。

### 3.4 服务与运维层

通过真实 HTTP 调用提供至少一个面向用户的接口；有健康检查，能指出数据或索引版本。受控工具采用参数验证与固定查询，不接收任意 SQL 或任意命令。至少完成 20 个请求的实际负载记录，报告延迟、错误和统计方法。

如采用请求体中的 `role`，必须写明它只是课程情境的角色输入，不是可信身份认证。服务默认绑定本机回环地址，接口调用与负载验证均在本人笔记本上完成。

## 4. 整体方案的必写内容

方案建议 5—8 页等量内容，重点是决策可审查，不能以页数代替质量。

1. 用户、问题、一次输入到输出的具体示例。
2. 范围：必须完成的能力、明确不纳入本项目的需求。
3. 架构图：数据流、模块职责、服务边界、持久化位置。
4. 数据契约：字段/类型/主键/时间/异常策略/文档版本和可见性。
5. 两项本人核心改动：动机、算法或状态变化、代码位置、验证方法。
6. 质量、计算、检索、服务、恢复与治理的验收表。
7. 资源与成本计算：硬件、数据规模、模型选择；模拟费用与真实费用分开。
8. 实施步骤、风险、备用路径与 AI 使用边界。

请先形成方案初稿，再根据真实实验修订，并保留关键变更理由。最终方案须描述实际交付架构，不能保留已经放弃却写得很完整的功能。

## 5. 实施步骤与成果核对

| 步骤 | 需要形成的产物 | 核对方法 |
|---|---|---|
| 明确问题与范围 | 用户问题、方案初稿、边界数据、验收表 | 说明用户能看到什么、数据从哪里来、两项改动是什么 |
| 跑通完整路径 | 输入→处理→HTTP 结果 | 在本人笔记本真实调用一次接口并保存结果 |
| 实现核心改动 | 两项关联改动、可手算边界数据、批处理对照 | 用独立参照验证改动对结果的影响 |
| 注入失败并恢复 | 重放、中断、恢复、拒答、权限与版本证据 | 至少一项失败被检测并恢复，不把错误包装为成功 |
| 冻结并验收 | 冻结记录、测试集结果、负载结果、运行说明 | 完成 dev 和修复后 freeze→test；已看过 test 后的重评标记为回归检查 |
| 复建并整理交付 | 本人笔记本上新目录中的重建结果、交付包和演示 | 按 README 从输入构建到真实接口调用，核对文件和版本 |

先跑通一个统计查询和一个证据问题，再完成选定改动。对不能支持核心用户问题的附加功能，可以从方案中删去并说明理由。

## 6. 必交文件

建议压缩包命名为 `BDP_学号_姓名_综合项目.zip`。压缩包内至少有：

```text
BDP_学号_综合项目/
  README.md                 # 环境、安装、数据构建、启动、验收、停止
  项目方案.md                # 最终整体方案
  项目报告.md                # 实际结果、核心改动、失败恢复与局限
  AI使用记录.md           # 仅使用 AI 助手者提交
  requirements.txt          # 实际采用的锁定依赖或课程依赖引用
  coursekit/                # 使用/修改过的课程代码，标出版本
  project/                  # 本人新增代码、配置、数据契约、验收数据
  evidence/                 # 09 的运行 JSON/同名 HTML、截图；原始结果及对应旁证
  artifacts/                # 按来源收据与哈希关联的原始数据
  submission-manifest.json  # 材料齐全后由 CLI 生成
  diff/                     # 与课程基线的差异或修改对照表
```

报告正文必须写本人学号、项目号 09，并逐图索引 run_id、JSON/HTML 和原始结果。复用课程上游时，前章 JSON 保留原编号；用于本项目评分的结果视图通过 `capture --lab 09` 重新实际运行。服务新终端设置 `$env:BDP_EXPERIMENT_ID='09'` 后启动。所有截图含原生学号、09、run_id 和真实结果，原始文件与 `*.identity.json` 一并提交。HTTP 每次响应自动归档到 `outputs/lab09/evidence/`；在 `/evidence` 点击本次 JSON/HTML 下载链接原名成对保存，或使用 `/docs` 响应中的两个 URL。不能只截图而不交对应运行 JSON/HTML。

材料齐全后在课程根目录执行（目录和报告名换成实际值）：

```powershell
.\.venv\Scripts\python.exe -m coursekit submission-manifest --lab 09 --directory .\提交\综合项目 --report 项目报告.md
```

授课老师将核对报告与清单，并逐张复核截图。待复核不等于通过；身份缺失、UNREGISTERED 或不一致须退回补证。该前提不改变下面的 100 分表。

课程代码允许以固定的仓库提交和完整补丁替代，但提交中要写明可取得的固定版本。不要打包 `.venv`、模型缓存、全部中间大文件或无关目录；如果省略可重建数据，必须给出确实可运行的生成方法与散列。演示视频以文件提交，须显示一次真实请求、一项边界案例和一项本人改动。

## 8. 失败标准与补验

以下为结果判定，区别于一般功能缺陷：

- 只有方案或截图，无法提交可运行源码和数据重建方法：视为缺少 MVP，项目总分不超过 49 分。
- 完全复跑课程包，没有两项可验证的本人关联改动：无法通过独立项目要求，项目总分不超过 59 分。
- 主线无法运行但能定位为一个局部环境错误：可申请一次补验；按补验后的实际结果评定，单次网络下载失败不会直接否定项目。
- 隐瞒越权泄漏、旧索引失配或数据重复生效，并以伪造 PASS 代替修复：相应正确性/治理项不得分；伪造证据按学校学术诚信规定处理。
- 选择模型路径后下载或运行失败：可切换到基础路径并完成其全部评价任务，按实际覆盖提交证据，并在报告中写明切换原因和最终使用的检索器、生成器。

普通失败案例若已被正确拒绝、定位并解释，可以是有效验收证据。验收重点不是“所有输入都返回成功”，而是系统按契约处理成功、拒绝与恢复。

## 9. 现场说明准备

授课老师可能从下列动作中选择 2—3 项，请同学们现场说明或操作：解释一条数据如何进入最终结果；重复提交一批事件；修改一个质量阈值；解释一个查询为何拒答；展示旧版本怎样被发现；指出一次 HTTP 变慢位于哪个阶段；对本人算法做微小输入变式。

现场独立环节不用 AI。同学们可以查阅自己的代码和报告；能解释并验证自己的实现，比背诵框架定义更重要。具体操作与方案写法见 [项目方案手册](项目方案手册.md)。
