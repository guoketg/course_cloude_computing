## 1. 为什么最后一个实验不是再接一个框架

前七次实验已经完成数据采集、质量处理、并行计算、故障恢复、知识检索、模型对照和 HTTP 服务。最后一步不是把所有按钮点亮，而是确定“当前这组数据、索引、代码和评价是否还相互对应，是否有明确的失败处理”。

本次把治理要求变成实际检查。程序会读取真实 manifest，检索真实索引，在临时副本中更新政策并篡改索引，在实际 SQLite 数据的内存副本中重放和回滚，再核验评价与 HTTP 证据。检查失败后保存原因并以非零退出，不允许把结果写成固定 PASS。

当前发布门禁的范围是**本机 extractive 摘录服务**。实验 06 的真实 LLM 对照即使存在引用或事实错误，也必须保留；本门禁通过不代表 LLM 可以生产发布，不代表获得生产安全认证，更不代表已经部署真实公有云。

## 4. 阶段二：理解检查是怎样产生结论的

### 4.1 检查包装函数

```python
try:
    detail = operation()
    checks.append({"name": name, "passed": True, "evidence": detail})
except Exception as exc:
    checks.append({"name": name, "passed": False, "error": str(exc)})
```

`passed=True` 只发生在实际 operation 正常完成之后。每个 operation 中有真实读文件、查询或断言。异常被收集，让你一次看到多项问题；末尾的 `all()` 决定整体能否发布。

```python
passed = all(row["passed"] for row in checks)
if not passed:
    raise RuntimeError("发布检查失败")
```

这种“收集所有证据后统一失败”的方式适合课堂排错。本课断言按普通 Python 运行，不要使用会关闭 assert 的优化启动选项。

### 4.2 哈希证明什么

`validate_index()` 检查实际文件的 SHA256 是否等于 manifest。它能发现意外修改和陈旧产物，但哈希不是数字签名。如果攻击者同时控制数据与 manifest，单纯哈希不能证明发布者身份。

因此不能写“SHA256 保证内容真实”。本课程只是检查字节完整性与版本一致性。来源授权、审核、签名与访问权限是其他层的责任。

### 4.3 当前索引为什么继承统计版本

政策问答与统计工具共享同一发布单元。索引版本包含实验 04 统计快照哈希，便于一次发布说明明确“这批政策和这份统计属于同一课程快照”。这个保守方案可能让仅统计变化也要求重建索引；大型系统可进一步拆分版本与独立发布单元，但必须明确一致性语义。

## 5. 阶段三：权限与隔离检查

公开检索使用 k=20，覆盖所有允许资料，检查每一项的 visibility。内部检索同时作为正例，确认维护政策确实存在且能被内部角色找到。

```python
assert all(h["visibility"] == "public" for h in public)
assert any(h["doc_id"] == "maintenance" for h in internal)
```

仅验证“公开请求没返回蓝鹭”是不够的：如果检索器坏到所有请求都为空，也能通过这种检查。加入内部正例后才能区分“边界有效”与“系统完全不可用”。

隔离检查确认 untrusted 和 retired 不进入索引，并发送固定攻击问题。它证明本课程这条攻击被拒绝、已知不可信资料被隔离。它不证明所有自然语言变体、编码方式或真实模型都不会受到提示注入。

默认服务只做摘录，没有文件删除、发送邮件或任意工具执行接口。因此“资料中的指令没有被执行”的能力边界应从实际可执行动作来说明，而不是用一句提示词承诺。

## 6. 阶段四：真实版本变更与索引篡改

`version_check()` 使用 `TemporaryDirectory` 创建自己的临时目录，复制政策，再加入 quota v3：“学生每周CPU推理配额已经调整为180分钟”。所有改动都在临时副本中完成，不改变主工作区的120分钟政策。

顺序如下：

1. 对复制的语料建立旧索引，保存旧版本；
2. 添加v3，使源文件SHA256变化；
3. 验证旧索引必须抛出 StaleIndexError；
4. 重建后确认 quota 只剩v3；
5. 比较旧版、新版、不同role的缓存键；
6. 向索引文件末尾添加空格，再次验证哈希不一致。

```powershell
.\.venv\Scripts\python.exe -c "from coursekit.common import OUT,read_json; r=read_json(OUT/'lab08/release_checks.json'); print(next(x for x in r['checks'] if x['name']=='version_and_cache'))"
```

应能看到 `stale_rejected=true`、`tampered_rejected=true`、不同的旧/新版本和三个不同缓存键。你应解释：字节级篡改检测可以拒绝一个只增加空格的文件，为什么这既是保证也是成本。

## 7. 阶段五：真实数据库副本中的重放和回滚

门禁按 latest.json 找到实验 04 数据库，以只读方式打开原库，重新聚合每个 service 的请求与 token 总量，逐行与实时汇总比较。若两边不一致，即使文件都存在也不能通过。

随后 SQLite 的 `backup()` 把实际数据库复制到内存。重复插入一条已存在事件：

```python
probe.execute("INSERT OR IGNORE INTO events VALUES (...)", sample)
probe.commit()
assert count_after == count_before
```

此处省略号仅用于展示逻辑，实际源码根据字段数生成占位符，不可将这段当完整SQL复制运行。event_id 主键阻止相同事件重复入库，行数保持不变。

再开启事务，将一条事件 input_tokens 增加999，但不提交，而是 rollback。回滚后重新读取整行，要求与原样本完全相等。

```python
probe.execute("BEGIN")
probe.execute("UPDATE events SET input_tokens=input_tokens+999 WHERE event_id=?", (event_id,))
probe.rollback()
assert recovered == sample
```

这是对真实数据副本的实际操作，不是写死“支持恢复”。但它也有边界：这里只复核重放与事务回滚，完整的消费进度与故障恢复链路证据仍来自实验 04。单机 SQLite 回滚不等于已经实现跨机器分布式 exactly-once。

默认20000个初始合法事件加实验04的一条故障恢复新增事件和一条晚到事件后，当前数据库通常为20002行。若你用不同规模，应该以最新运行记录解释，不能硬编码20002作为所有数据集的真值。

## 8. 阶段六：评价与HTTP证据为什么也要检查版本

`evaluation_check()` 要求测试报告的 index_version 等于当前索引，并核对 questions.jsonl 的SHA256、测试题qid集合和逐题数。只有总分没有逐题证据，不足以验收。

课程摘录服务门槛为 Recall@3 ≥ 0.75，并且固定测试负例全部拒答。该门槛针对本合成题集；不能把这份小测验的“全通过”外推为真实世界性能保证。

`service_check()` 检查请求数至少20、逐条响应状态200、无错误且health记录中的索引版本与当前一致。它是对实验07实际输出的可追踪核验，不会伪造新的网络测试。

如果索引变化，需要按顺序重新运行：

```powershell

.\.venv\Scripts\python.exe -m coursekit lab07 --requests 20
.\.venv\Scripts\python.exe -m coursekit lab08
```

第二条需要实验07的服务仍在运行。若只是课程中的测试集调试，报告必须注明测试集已被查看，不能把重跑声称为未见测试。这里重跑的目的是版本一致性验证。

## 11. 发布说明与恢复手册

在个人报告中写一页发布说明，至少包含以下可复查项目：

| 项目 | 应填写的实际内容 |
|---|---|
| 服务范围 | 本机摘录问答、固定统计工具，role是教学模拟 |
| 数据身份 | 文档SHA256、统计SHA256、索引版本、数据库run_id |
| 模型对照 | 真实模型ID/revision/digest，成功、失败或SKIP，不能隐去错误 |
| 评价证据 | 测试报告文件、题集哈希、分组指标及人工忠实度限制 |
| HTTP证据 | 请求数、错误数、p95、缓存预热情况 |
| 发布判定 | 7项或个人新增8项的真实结果，失败项及原因 |
| 已知限制 | 合成小题集、单机SQLite、单进程缓存、无真实认证 |
| 恢复步骤 | 哪一层变化后重跑哪些命令，以及保留哪些历史证据 |

恢复原则是根据依赖关系处理，不是遇到任何错误就删除data重来。例如文档变化：重建索引 → 重跑评价 → 重测HTTP → 重跑门禁；服务仅重启：缓存丢失，数据版本不变，重新测量并说明冷/热状态。

撤回政策时，要保证最新撤回状态不会复活旧版。真实系统删除个人数据还需要处理原始资料、索引、副本和缓存；本课程用虚构数据讨论这一流程，不处理真实个人敏感资料。

## 13. AI边界、分析题与提交

AI可以帮助解释异常、审查恢复说明的语言、查哈希与SQLite官方API。必须自己完成依赖图、失效传播预测、新增检查逻辑、隔离状态对照和发布判定。不得让AI生成“看起来都通过”的日志、篡改评价、或把未执行的云/模型操作写成实测。

报告至少回答：
